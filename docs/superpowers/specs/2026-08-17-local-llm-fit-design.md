# ローカルLLM適合チェッカー 設計

GPUを選ぶと、実用品質で動かせるローカルLLMと推奨量子化を一覧で出すWebツール。

## 解こうとする問題

ローカルLLMを動かしたい人が最初にぶつかるのは「自分のGPUでどのモデルが動くのか」である。
既存のVRAM計算機はモデルファイルがVRAMに収まるかしか見ない。
しかし実際には、収まっても品質が実用に届かない量子化レベルがあり、MoEモデルならエキスパートをCPU側に逃がすことで見かけ以上に大きいモデルが動く。

このツールは「収まるか」ではなく「実用に足るか」を判定する。

判定基準の根拠は [[project-local-llm-quantization]] の検証（RTX 5070 Ti 16GB での実測を含む）。

## 判定ロジック

入力はGPUのVRAM容量とコンテキスト長。各モデルを次の5つに分類する。

| 分類 | 条件 |
|---|---|
| 余裕あり | 推奨量子化で収まり、余剰が1GB以上ある |
| ギリギリ | 収まるが余剰が1GB未満。長い文脈で溢れる可能性がある |
| 量子化を下げれば動く | より低い量子化なら収まる。**Q3_K_M未満になる場合は「非推奨」と明示する** |
| オフロードなら動く | MoEモデルで、エキスパートをCPU側に置けば収まる |
| 動かない | 上記のいずれにも当てはまらない |

### 必要VRAMの計算

```
必要VRAM = モデルファイルサイズ + KVキャッシュ + オーバーヘッド
```

- **モデルファイルサイズ**: Hugging Face APIが返すGGUFファイルの実サイズ
- **KVキャッシュ**: `2 × num_hidden_layers × num_key_value_heads × (hidden_size / num_attention_heads) × context_length × 2バイト`（FP16換算）。パラメータは各モデルの `config.json` から取得する
- **オーバーヘッド**: 0.8GB を定数とする（llama.cpp の計算バッファとフレームワークの占有分）

**この値は推定である。** UIに推定値である旨を明記し、実測で確認できているのは RTX 5070 Ti 16GB のみであることを併記する。誤判定で信頼を失うほうが、判定を出さないより損失が大きい。

### 量子化レベルの判定

GGUFのファイル名から量子化レベルを抽出する（`Q8_0`, `Q6_K`, `Q5_K_M`, `Q4_K_M`, `Q3_K_M`, `Q2_K` など）。
品質順に並べ、VRAMに収まる最上位を推奨とする。

**Q3_K_M を実用の下限とする。** これ未満（Q2_K など）しか収まらない場合は、収まっていても「非推奨」を明示する。denseパラメータの多いモデルでは劣化が大きいため。

### MoEの判定

モデル名の `A<数字>B` パターン（`Qwen3.6-35B-A3B` の `A3B` = active 3B）、または `config.json` の `num_experts` 系のキーで判定する。
MoEと判定された場合、エキスパートをCPU側へオフロードする構成（llama.cpp の `--override-tensor`）を提案し、その場合の必要VRAMを active パラメータ基準で再計算する。

## データ

- **モデル**: Hugging Face API から取得する。GGUF形式のリポジトリをダウンロード数の多い順に**50件**取得し、各モデルの `config.json` を併せて読む（50件はキャッシュとAPIレート制限に収まる範囲として設定した。表示件数が不足するようなら増やす）
- **GPU**: 手動のJSON（`data/gpus.json`）。型番とVRAM容量のみ。GPUは数十種類で容量も変わらないため更新負担にならない
- **API中継**: Cloudflare Pages Function（`functions/api/hf.js`）が Hugging Face API を中継する。CORS回避、レート制限対策、レスポンスのキャッシュを担う。ergochair の `functions/api/rakuten.js` と同じ構造

## 収益化

Amazonアソシエイトを使う。ただし **PA-API は審査通過後（180日以内に3件の適格販売）でないと使えない**。

- **初期**: GPU名でAmazon検索へ飛ぶアソシエイトタグ付きリンクを置く。APIを使わないため審査前でも動く
- **審査通過後**: PA-API で価格と在庫を表示する
- **価格の手動記載はしない**（PA-API以外から取得した価格の掲載は規約違反）
- サイトにアソシエイト参加の明記を入れる

## 技術構成

| ファイル | 役割 |
|---|---|
| `index.html` | UI、結果の描画 |
| `src/fit.js` | 判定ロジック（純関数。DOMにもネットワークにも触れない） |
| `src/fit.test.mjs` | `node --test` による単体テスト |
| `data/gpus.json` | GPU型番とVRAM容量 |
| `functions/api/hf.js` | Hugging Face API の中継（Cloudflare Pages Function） |
| `serve.py` | ローカル開発用の静的配信とAPI中継 |

ホスティングは Cloudflare Pages（費用ゼロ）。
判定ロジックを純関数に隔離するのは、ブラウザを起動せずテストするため。ergochair と同じ構成にして設計判断を再利用する。

## スコープ

**作るもの**: GPU選択、コンテキスト長の指定、モデル一覧と4分類の判定、推奨量子化の表示、Amazon検索リンク。

**作らないもの**: ユーザー登録、価格表示（審査前）、画像生成モデルの対応、モデル同士の性能比較。

## 検証

- 判定ロジックは `node --test` で確認する。特に境界（余裕ありとギリギリの境目、Q3_K_M の下限判定、MoEのオフロード計算）を対象にする
- **RTX 5070 Ti 16GB での実測値と突き合わせる**。gpt-oss-20b が 15.1GB、gemma-3-27b-it が 14.3GB という既知の実測があるため、これらを回帰テストの基準にする
- Hugging Face API の応答が変わった場合に備え、テストは保存したレスポンスで動かす
