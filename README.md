# ローカルLLM適合チェッカー

GPUを選ぶと、実用品質で動かせるローカルLLMと推奨量子化を一覧で表示するWebツール。

https://github.com/kiskyk/local-llm-fit

## 解こうとした問題

ローカルLLMを動かしたい人が最初にぶつかるのは「自分のGPUでどのモデルが動くのか」である。既存のVRAM計算機はモデルファイルがVRAMに収まるかしか見ない。しかし実際には、収まっても品質が実用に届かない量子化レベルがあり、MoEモデルならエキスパートをCPU側に逃がすことで見かけ以上に大きいモデルが動く。

このツールは「収まるか」ではなく「実用に足るか」を判定する。

## 判定の考え方

必要VRAMを次の式で見積もり、5つに分類する（余裕あり／ギリギリ／量子化を下げれば動く／オフロードなら動く／動かない）。

```
必要VRAM = モデルファイルサイズ + KVキャッシュ + オーバーヘッド0.8GB
```

- **Q3_K_M を実用の下限とする。** これ未満（Q2_K など）しか収まらない場合は、収まっていても非推奨と明示する。denseパラメータの多いモデルでは劣化が大きいため
- **MoEモデルはエキスパートをCPU側へオフロード**（llama.cpp の `--override-tensor`）すれば、activeパラメータ相当のVRAMで動く。16GBでも35B級MoEが動くのはこのため
- オーバーヘッド0.8GBは RTX 5070 Ti (16GB) での実測（gemma-3-27b-it 14.3GBで余裕0.9GB、gpt-oss-20b 15.1GBで余裕0.1GB）と整合する値で、回帰テストとして固定している

判定は推定値であり、実測で確認できているのは RTX 5070 Ti (16GB) のみ。

モデル情報は Hugging Face API から自動取得する（GGUFリポジトリをダウンロード数順に50件）。HF APIの `config` は要約版でレイヤー数を含まないため、KVキャッシュは `gguf` メタデータのパラメータ数から概算する（約20KB/トークン/1Bパラメータ）。

## ローカルで動かす

```
python serve.py
```

http://127.0.0.1:8772 を開く。`serve.py` が静的配信と Hugging Face API の中継（`/api/hf`）を兼ねる。本番は Cloudflare Pages で、中継は `functions/api/hf.js` が担う。

## テスト

```
node --test src/fit.test.mjs
```

判定ロジックは `src/fit.js` に純関数として隔離してあり、ブラウザなしで検証できる。
